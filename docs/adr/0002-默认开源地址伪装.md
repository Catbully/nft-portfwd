# 0002 · 端口转发默认开源地址伪装

## 状态

已采纳（由实测推翻了最初的默认值）。

## 背景

最初的判断是"默认不伪装，保留客户端真实源 IP，落地目标的日志才有意义"。这个判断在真机上被证伪。

实测条件：转发节点 `aws-hk`（公网），落地目标 `1.1.1.1:80`（公网），客户端 `aws-jp`（公网）。

- 不开伪装：DNAT 规则计数器涨到 `packets 1 bytes 60`，说明 SYN 到达并被改写，但客户端 `curl` 在 6 秒后超时（`connect=0.000000`，exit 28），连接从未建立。
- 开伪装：同一个 `curl` 在 0.11 秒内拿到 HTTP 响应。

原因：DNAT 只改写去程。不开伪装时落地目标的回包源地址是它自己、目的地址是客户端，于是它按自己的路由表直接发给客户端，绕过转发节点。客户端内核里这条连接的对面应该是"转发节点的 IP:本机端口"，收到的却是"落地目标 IP:目标端口"，conntrack 对不上，直接丢弃。

## 决策

转发规则的默认行为是：在 `postrouting` 对**落地目标地址**做 `masquerade`。`--no-snat` 关掉它。

匹配条件写成 `ip daddr { <落地目标...> } masquerade`，而不是笼统的 `ct status dnat masquerade`——后者会连带伪装掉同一台机器上 Docker 之类的其它 DNAT，属于越界。

## 后果

- "公网 → 转发节点 → 公网"这个最常见的中转场景开箱即通。
- 落地目标看到的源地址是转发节点，客户端真实 IP 丢失。需要按客户端做访问控制时，这个方案不可用，得上应用层中继。
- 落地目标的回程本来就经过本机时（目标在本机后端、或目标的默认网关就是本机），伪装是多余的，会多一跳 NAT；这种场景用 `--no-snat`。
- 只在有转发规则时才生成 `postrouting` 链；纯放行的规则清单不会凭空多出一条 masquerade。

## 被否决的替代方案

- **默认不开，让用户自己发现**：失败现象是"连上了但没响应"，与防火墙丢包、目标端口没开的表现几乎一样，排查成本远高于多一行 NAT。
- **`snat ip to <本机出口 IP>`**：需要先探测出口地址，多网卡/多 IP 的 VPS 上会选错；`masquerade` 让内核自己选，且天然跟随出口变化。
